SIDONPAY Business Intelligence & Customer Analytics

Tools: Power BI · Python · pandas  
Project Areas: Business Intelligence · Customer Segmentation · Transaction Analysis · Executive Dashboard Development

1. Project Overview

This project focused on business intelligence and customer transaction analytics for SIDONPAY, a fintech payment platform. Using a simulated transaction dataset, I applied Python, pandas, and Power BI to examine transaction behaviour, segment customers based on transactional characteristics, evaluate payment activity, and develop an executive dashboard to support business monitoring and decision-making.

The project aimed to transform structured transaction data into meaningful analytical insights about customer activity, transaction patterns, and simulated platform operations.

Data disclaimer: The dataset used in this project was simulated. The analysis does not represent verified SIDONPAY customer transactions or actual operational performance.

2. Project Objectives

The main objectives were to:

- Analyse customer transaction behaviour and identify common transaction patterns.
- Examine average transaction values, transaction frequency, and preferred transaction types.
- Investigate peak transaction hours and changes in transaction volumes over time.
- Explore customer balance trends and transactional activity.
- Segment customers using transaction-based behavioural characteristics.
- Evaluate patterns in the simulated payment platform's operational activity.
- Develop an executive dashboard in Power BI to present analytical insights in an accessible visual format.

4. Project Methodology

4.1 Data Preparation and Analysis

Python and pandas were used to work with the simulated transaction dataset and prepare data for analysis.

The analysis examined transaction records and relevant customer-level characteristics to support behavioural analysis, customer segmentation, and operational monitoring.

4.2 Customer Transaction Behaviour Analysis

I analysed transaction behaviour across several dimensions:

- Transaction types: Examined the distribution of transaction categories to understand which types were more common.
- Average transaction value: Investigated the average value of transactions to understand transaction-value patterns.
- Transaction frequency: Examined how frequently customers conducted transactions.
- Peak transaction hours: Analysed transaction activity across different hours to identify periods of higher activity.
- Customer balance trends: Examined account balance patterns to understand how balances varied across customers and over the available data.

These analyses provided a structured approach to understanding transactional behaviour within the simulated dataset.

4.3 Behaviour-Based Customer Segmentation

I performed customer segmentation using transactional characteristics rather than demographic attributes.

The dataset did not contain demographic information, so the segmentation focused on observable transaction-related variables, including:

- Transaction frequency.
- Average transaction amount.
- Preferred transaction type.
- Account balance.
- Transaction activity.

This approach explored how customers could be grouped according to their financial activity and transaction behaviour.

The segments should be interpreted as behaviour-based analytical groupings rather than demographic profiles. Their usefulness for real-world business decisions would require validation against actual customer data.

4.4 Operational Performance Analysis

I evaluated the operational activity of the simulated payment platform by examining transaction patterns over time.

The analysis focused on:

- Identifying periods of high transaction activity.
- Analysing the distribution of transaction types.
- Assessing how transaction volumes changed over time.
- Examining hourly transaction patterns to identify periods of increased activity.

These dimensions helped frame how transaction data can support operational monitoring and inform further investigation of platform activity.

Because the data was simulated, the analysis cannot establish actual platform capacity, service reliability, payment failure rates, or production performance.

4.5 Executive Dashboard Development

I used Power BI to develop an executive dashboard for presenting key transaction and customer analytics.

The dashboard was intended to make the analysis more accessible by organising relevant measures and visualisations into a consolidated view.

The analytical areas covered included:

- Transaction activity and volume.
- Transaction types and average transaction values.
- Customer transaction frequency and behavioural segments.
- Transaction activity by time period.
- Customer balance trends.

The dashboard connected customer-level analysis with broader transaction activity to support interpretation and business monitoring.

5. Key Analytical Areas

The project explored five main areas of business intelligence.

Customer behaviour: Understanding how frequently customers transact, their average transaction values, and their preferred transaction types.

Customer segmentation: Grouping customers based on transactional characteristics without relying on unavailable demographic data.

Transaction patterns: Examining transaction distribution, peak activity hours, and changes in transaction volumes over time.

Balance trends: Exploring variations in customer account balances within the simulated dataset.

Executive reporting: Presenting transaction and customer insights through a Power BI dashboard designed for accessible business reporting.

Specific numerical findings and segment sizes are not reported in this README because the corresponding verified results have not been included here.

7. Limitations

This project has several limitations:

1. Simulated data: The dataset does not represent verified production transactions or actual SIDONPAY customer records.
2. No demographic variables: Customer segmentation was based on transactional characteristics, not age, gender, location, or other demographic attributes.
3. Limited external validity: Patterns identified in simulated data may not reflect actual customer behaviour or operational conditions.
4. No confirmed business impact: The project does not establish improvements in revenue, customer retention, transaction success rates, or operational efficiency.
5. Limited operational indicators: Transaction volume and timing alone cannot establish payment reliability, system capacity, or the causes of activity changes.
